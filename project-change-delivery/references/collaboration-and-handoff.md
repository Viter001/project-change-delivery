# 轻量协作与中断接手

适用于已有协作工具的任务委派，以及一个代理因额度耗尽、异常或会话结束后由另一个代理接手收尾。不规定具体模型，不安装新工具，不要求专门的任务板或消息总线。用户记录复用 QUESTIONS.md、FEEDBACK.md、DEVLOG.md、DISCUSSION-LOG.md 和 Git；详细运行和交接记录按 [记录分层](record-layers.md) 放入 agent 目录，已有等价工具载体继续沿用。

## 使用现有工具委派

在用户授权范围内复用当前协作工具，例如 dsh-crew；按实际可用接口派发，不猜命令，也不因为本规则存在就自动启动多代理。

派发时一次说明：任务目标及完成条件、必要上下文、允许修改的文件或职责边界、已有成果、不能改的内容、要求返回的成果及验证结果。只给完成任务必要的背景，不默认复制整个聊天。

每个任务明确一个当前执行者。子任务存在依赖或写入范围重叠时顺序执行；确有独立任务才并行。并行写入需要明确隔离或文件归属，不能只凭“各自小心”避免覆盖。若共享同一 Git 工作目录，暂存和提交由协调者串行执行，执行者交回变更；若使用独立 worktree，则分别提交后由协调者核对集成。四条规则要求提交，但不要求多个代理并发操作同一暂存区。

执行者返回：完成／部分完成／受阻、实际改动、提交或文件位置、执行过的检查及结果、未完成项。主代理核对成果与完成条件，再接续或交付；自报完成不等于实际完成。仅当风险或任务需要时安排独立评审，不为简单任务固定增加一个评审代理。

利用工具现有进度与结束状态跟踪。工具持续无结果时先查看状态、可见输出和成果，再决定等待、停止或接手；不无依据反复启动相同任务。重新派发前先确认原执行者不再写同一范围。共享 Issue、开发日志及 GitHub 同步由当前协调者汇总更新，避免多人并发写同一管理文件。

## 中断接手流程

### 1. 恢复目标，不从差异猜任务

先读用户最新要求、Issue、开发记录摘要及已批准决定确认目标，再读该任务的 agent 恢复摘要，必要时按证据链接读取日志。Git diff 表示发生了什么，不表示用户要求什么。目标明确时直接继续；只有缺失信息会改变结果时才询问，先推进不依赖该信息的部分。

### 2. 确认写入者状态

检查前一个代理及其已委派任务是否停止；主会话没额度不代表所有子任务或后台写入都停止。优先通过原协作工具核对任务状态。无法确认时只读核对或处理不重叠范围，对重叠写入先澄清，不擅自杀未知进程。明确接手者后再修改共享范围。

### 3. 核对工作区与任务基线

先确认具体项目、分支和工作目录，再定向检查：

```text
git status --short
git diff --stat
git diff
git diff --cached
git ls-files --others --exclude-standard
git log -n 10 --oneline
```

命令是起点，不是固定检查上限。只阅读与任务相关的内容；未跟踪文件可能是核心成果，也可能是用户资料，不能默认删除或提交。暂存内容不自动代表本次授权范围。

结合任务记录确定起始提交 BASE 和当前 HEAD；任务可能已有多个提交，要检查 BASE 到 HEAD 的相关改动，再加上暂存、未暂存和未跟踪成果。不能用 HEAD~1 自动充当任务起点。起点不明确时按记录、相关文件历史逐步定位，注明不确定性，不随意把所有近期提交算入任务。

不使用 reset、clean、stash 或批量覆盖来“整理”接手现场。保留用户和其他代理的改动；混在同一文件中的无关改动需分辨后定向修改与暂存。没有 Git 时依据文件和记录接手，明确缺少历史基线，按入口规则处理建库前提。

### 4. 分类并继续

| 成果状态 | 接手动作 |
| --- | --- |
| 已完成且有适用验证证据 | 保留成果；确认相关部分之后未改变，不重复实现 |
| 已实现但未验证，或验证结果未记录 | 补相关检查；“运行过”不能算通过 |
| 未完成或不满足目标 | 接续实现，验证受影响范围 |
| 与本任务无关或归属不明 | 保留，不混入本次修复或提交 |

历史验证需对应内容、环境和范围；检查运行后有相关修改、依赖变化或证据缺失时重验。有效历史结果可引用并标明来源，不说成此次重跑。若既有失败阻断当前交付目标，在授权范围内处理；不因为失败早于接手就忽略。

### 5. 收尾

核对最终成果与任务完成条件，更新 Issue 和开发记录，写明接续了什么、补了什么、验证结果与剩余事项。对尚未提交的本次相关成果执行检查后创建中文提交；不要重写已有提交。若只有只读核对、没有文件改动，不制造空提交。推送、发布及 GitHub 同步仍按各自授权与明确触发规则执行。

## 在工作过程中留下恢复点

不要依赖终止前生成交接报告。在形成有意义的提交、完成关键验证、改变方案或遇到阻塞时，及时更新本次运行的 `checkpoint.md`；将实质对话推进记入 DISCUSSION-LOG，重要裁决更新 Question，阶段成果汇总到 DEVLOG。小任务可合并记录一次，无需逐次工具调用记流水账。

恢复点最少包含：关联 Issue／目标、工作分支与可确定的任务基线、已有成果或提交、验证范围与结果、剩余工作、仍运行的委派任务及负责人。未知项注明未知，不编造完成状态。不记录密钥或内部隐私推理。

示例：

> FB-007：导出日期。正文修改已提交，测试仍有未提交修改；当前验证仅覆盖预览，实际导出待检。已停止本次委派任务。接手后先检查未跟踪的测试夹具，再补导出验收；用户另有封面改动，不纳入本次提交。

上例写入 `.agent/runs/<task-id>/<run-id>/checkpoint.md`，不直接写入 DEVLOG。DEVLOG 可简记“日期修复进行中，预览已验证，实际导出待检”；无需用户阅读运行日志。没有恢复点也不自动停工，依现有成果和目标重建状态后继续。
