# 项目视图与注意力

调整本流程时，以 [设计哲学](design-philosophy.md) 作为取舍依据。

全景回答项目往哪里走：目标、当前阶段、阶段完成条件、议题状态和下一步。关系视图与全景放在一起，以网络呈现依赖、阻塞、关联和取代关系；只画有来源的关系。注意力视图作为默认入口，回答现在需要用户做什么。沿用项目现有载体，视图是主记录的投影。

## 请求与成果分开

每个注意力请求包含：关联事项、需要谁做什么、为什么必须由人处理、现在的触发依据、解锁的结果、建议与证据。准入依据是实际阻塞、已约定的阶段验收节点或重要风险。真实风险即使尚未阻塞，也可提前请求介入。

代理可验证的事实直接验证并记录。非阻塞的主观体验、多个局部修复合并进入阶段验收候选，保留待验收状态，到约定节点集中呈现。用户沉默不等于验收通过。已答复的问题仅在出现会改变原判断的新证据时重新请求。

成果区说明已完成什么及证据，无需回复的成果明确标记。当前无准入请求时显示“当前无需你介入”，继续已授权工作。请求数量由实际需要决定；同一决定能处理的事项尽量合并，仍保留各自来源。

## 注意力投资回报率

定性评估预期推进与注意力成本，优先呈现能解除关键依赖、完成阶段或避免重大返工的请求。说明收益依据，未知收益标记待判断；不用事项数量、提交次数或虚构节省时间代替收益。

## 刷新

推进项目的会话更新主记录，再按项目约定刷新视图，记录来源和刷新时间。解决问题后移出请求区，保留成果及验收真实状态。重读现有待决事项及阶段目标后再筛选请求，使最新反馈融入项目进展。维护通用 skill 的会话负责规则迭代，具体项目状态在对应项目维护。

## 建立配套视图

用户要求建立视图或维护已有视图时，按 [生成与维护规范](project-view-generation.md) 在当前项目交付页面、派生摘要、筛选与生成方式、来源清单、维护入口和验证。
