# 管理记录分工与清单版式（v0.2）

## 选择主记录

| 信息 | 主记录 | 不该放什么 |
| --- | --- | --- |
| 当前产品能力、设计与版本范围 | 已有产品规划／规范 | 不用 Questions 代替产品说明 |
| 有影响的选择、范围变更、规范冲突 | QUESTIONS.md | 每轮聊天、开始执行、工具调用流水 |
| 当前问题与整改进度 | FEEDBACK.md | 把长排错报告作为唯一入口 |
| 一段工作的成果与验证结论 | DEVLOG.md | 按对话轮次重复展开需求 |
| 用户如何提出、纠正和推进工作 | DISCUSSION-LOG.md | 完整聊天转录、长命令输出、内部隐私推理 |
| 实时状态、恢复点、原始输出 | .agent/runs/ | 不代替用户决定或正式验收结论 |

同一事实只在主记录详细维护，其他文件只写与自身用途有关的一句摘要及链接。记录需要时更新，不要求每次回复都改所有文件。

## QUESTIONS：决策门槛与当前总览

只有能明确写出“需要决定什么，以及会影响什么”，且涉及方案取舍、范围／规范变化或冲突裁决时，才新建 Q。重要的已作决定也可登记，说明理由和适用范围，不假装仍待裁决。普通初始需求直接更新规划；“请整理文档”“开始实现”“调用某工具”默认记讨论过程或成果日志，除非其中另含有影响的决策。

同一问题后续讨论更新原 Q，不按对话轮次递增编号。多轮提出相同事项时补来源和变化，不新建平行问题。

文件顶部放当前待裁决表：编号、待决定事项、影响范围、需要谁决定、详情链接。暂无待裁决事项时明确写无；不要把已裁决历史混入当前待办。

已裁决区简记：决策问题、结论／理由、适用范围、日期与批准来源、落实状态及后续条目。决定与实现是两个状态。后续裁决取代旧结论时，在旧条目更新“已被 Q-xxx 取代”及链接，保留原文历史；不能让失效结论继续显示为当前待决或当前规范。

## FEEDBACK：先清单，再摘要与证据

文件开头是当前未关闭问题清单，每个问题一行：

| 编号 | 问题／现象 | 状态 | 下一步或阻塞 | 详情 |
| --- | --- | --- | --- | --- |
| FB-001 | 预览程序启动无窗口 | 已整改，待用户复验 | 用户从新入口启动确认 | 本条整改摘要／验收链接 |

这是格式示例，不是当前项目的真实问题。问题标题写用户现象，不用底层诊断代码充当标题。优先级和负责人仅在确有需要时加列，不制造必填空字段。

详情只保留来源、现象与期望、整改摘要、复验结论、关联 Question 和证据。长堆栈、寄存器、完整命令输出进 agent 日志；必须长期保留的技术证据进正式证据目录并链接。即便只有一条反馈，也提供总览。

当前表与详情在同一次更新中保持一致，不作为两套独立状态；阶段定义及远程同步以 issue-sync 规程为准。未执行的用户复验不能被自动化通过替代。正文只在详情维护，清单是投影视图，不另建同编号条目。

已完成或取消项移到已关闭区，保留编号、关闭理由和复验依据；积累多时按阶段归档并留索引，不能删历史。取消不等于修复成功。反馈涉及未批准范围时关联 Q 等待裁决，而非自动改类别。

## DEVLOG：阶段成果

按交付、阶段或一个有意义的工作单元组织，描述：完成了什么、重要变化、验证结论与限制、剩余问题，以及 Q／FB／讨论和提交链接。持续更新未结束的阶段条目，避免每轮都新增近似段落；阶段完成后保留历史，后续纠正另记或明确标注。

不复制需求讨论全文，不逐次记录“更新草稿 v0.x”“运行 diff 检查”。用户作出改变方向的决定，在成果摘要里说明影响并链接 Q；没有重要决定则不为凑字段新建 Q。

## DISCUSSION-LOG：逐轮复盘

面向用户复盘对话和工作推进，是精炼会话记录，不是机器实时日志。每轮有实质要求、建议、纠正、决定或工作推进时写一条 D-编号；“继续”“收到”等无新增信息的消息并入原条目。单轮内的工具调用和代理消息不各立条目。

条目包含日期（已知时可加时间）、主题、用户提出、本轮回应／实际处理、结果与未决事项、关联文档或提交。区分 agent 建议、用户批准和实际完成；不把回复建议写成已经执行。日期和来源按可验证记录填写，未知时间不得补造。

```markdown
## D-018：全局规划与 MVP 分离
- 日期：按实际对话日期记录。
- 用户提出：全局方向不应全部进入首版。
- 本轮处理：拆分全局规划与 MVP，撤回首版范围的过度推定。
- 结果：两份规划已更新，具体首版范围仍待确认。
- 关联：Q-014、规划文档及相应提交。
```

跨多轮的一项决定仍只有一个 Q；每轮 D 可引用它并描述当轮新增变化。工作推进轮只有完成结果也可记 D，但 DEVLOG 仅汇总交付成果，不重复整段。增长后按月或阶段归档到讨论记录目录并留索引，不更改 D 编号或造成断链。

## 迁移旧记录

只有用户授权整理实际项目时才迁移；升级 skill 本身不授权重写旧项目。保留原始材料与可追溯版本，先分类、建立旧编号／位置到新记录的映射，再定向整理。

普通对话型 Q 的内容可归入讨论记录或规划，但原 Q 保留重定向摘要，不回收编号。有效裁决保留 Q 身份及 GitHub 绑定，不能仅为缩短文件删条目。DEVLOG 的逐轮内容迁入讨论记录时保留日期和来源；原位置保留阶段摘要或索引。Feedback 先加当前表，再精简详情；不了解状态时标待核对，不能据历史文字推定关闭。增量同步应更新原条目，清单与归档索引不创建第二个远程 Issue。
