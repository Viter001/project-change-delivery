# 文档版式与更新方式

新建、整理或更新管理文档时使用本页。已有等价版式可保留，但必须满足相同的信息顺序与更新语义。以下方括号是填写说明，不是要原样写进项目的占位文字；无适用内容的可选字段直接省略，未知事实明确写未知。

## 通用排版

一份文件一个一级标题；二级标题组织主题或条目，三级标题仅用于必要子题。清单／对比使用表格，单项说明用短段落或同级字段，不套多层列表。相同职责使用稳定字段名与顺序。状态写在状态字段，标题写对象或问题；DEVLOG 可按下方格式用日期定位成果，验收可用版本定位证据，其他正文标题不串入日期、状态和全过程。

正文中的状态与来源只保留读者需要的信息。原始附件保留原件并链接，不整段复制；关联使用可定位链接。不得保留空模板字段或为填齐格式编造决定、验证、阻塞和批准来源。下表是选用依据，不是每次任务必须更新的文件清单。

| 文件职责 | 首屏 | 主体组织 | 更新方式 |
| --- | --- | --- | --- |
| README | 是什么、当前能做什么、从哪里开始 | 使用／开发入口、范围、文档导航 | 对应主题原位更新 |
| 规划 | 目标、范围、方向状态 | 按能力／阶段组织 | 合并有效方案，历史另存 |
| 规范 | 适用范围与有效版本 | 按规则／契约组织 | 更新规则和适用边界 |
| 指南 | 前提和操作入口 | 按使用者完成任务的顺序 | 更新具体操作与异常处理 |
| Q | 当前待决表 | 固定问题卡片 | 更新同一卡片字段 |
| Feedback | 未关闭问题表 | 固定整改卡片 | 更新整改和验收状态 |
| DEVLOG | 最近阶段成果 | 按成果单元 | 单元内更新，完成后保留历史 |
| DISCUSSION-LOG | 用途与可定位条目 | 按实质轮次 | 按 D 编号正序追加 |
| 验收 | 当前适用结论表 | 按版本／范围 | 新证据更新当前索引，历史保留 |
| agent checkpoint | 当前现场与下一步 | 固定恢复字段 | 替换为最新现场 |
| 项目视图 | 阶段、真正需要用户的事项 | 派生摘要与来源链接 | 主记录变更后核对并刷新 |

## Q：问题卡片

文件顺序：用途一句话 → 当前待决表 → 问题详情 → 已决／暂缓索引。当前表列为“编号｜待决定的问题｜影响｜触发时机｜详情”；暂缓事项不混入当前待决表。详情保留稳定编号和锚点，可继续按编号顺序排列，不为状态变化更换身份。

```markdown
## Q-编号：具体要决定的问题

- 状态：[待讨论／待决定／已决定／暂缓／已被取代；落实状态另列]
- 问题：[需要作出的选择或需要解除的冲突]
- 影响：[影响的目标、范围与约束]
- 待定内容：[尚未决定的具体部分；没有则省略]
- 当前结论：[有效选择及简要理由；未决定写“尚未决定”，建议不得当成结论]
- 落实：[一句当前落实情况，链接规划、整改或验收；无执行进展则省略]
- 依据与关联：[批准者、日期与来源链接；相关 Q／FB／规范；被取代时链接新决定]
```

已决定与已实现是不同状态。同一问题可有已确定部分和仍待定部分，分别填入对应字段。日期只用于来源定位，不用于在问题内追加事件段落。

更新时原位改字段，并同步当前表；不得追加“决策记录（日期）”“本轮处理”“日期补充”“实现／返修经过”来保存每轮事件。禁止只是把这些标题改名而保留同一流水。旧结论需要追溯时链接讨论日志或明确的历史归档，Q 正文只保留取代关系。产品规格和测试详情不复制进问题卡。

例如“许可证暂缓”应写为：状态＝暂缓；当前结论＝维持现有公开范围及未选许可的状态；待定内容＝未来许可与素材授权范围；依据＝用户确认日期及讨论链接。材料整理、仓库更名和上传进度进入各自成果／讨论记录，不连续追加到 Q 下。

## Feedback：问题清单与整改卡片

文件顺序：用途 → 当前未关闭表 → 详情 → 关闭索引。清单列为“编号｜用户可见问题｜状态｜下一步／阻碍｜详情”。

```markdown
## FB-编号：用户看到的问题

- 状态：[待核实／待处理／处理中／已整改待复验／已关闭／取消]
- 现象与期望：[实际表现及希望达到的结果]
- 来源：[反馈者、日期、原文或附件定位]
- 整改：[当前处理结果；长排查过程只给链接]
- 验收：[通过范围、依据与未验部分；未复验就明确写出]
- 下一步／关联：[尚需行动、阻碍或相关 Q；没有则省略]
```

同一问题返修时更新整改与验收字段，不叠加日期流水；关闭后移出当前清单，保留编号、原因与证据。不能把代理测试通过写成用户复验通过。

## DEVLOG：阶段成果

按阶段或最小完整工作单元设标题，最新在前。同一未结束单元更新原条目；交付后另有实质变化才另开成果。

```markdown
## 日期：阶段／成果名称

- 成果：[用户可理解的变化]
- 验证：[实际验证范围、结果及证据链接]
- 剩余：[未完成事项与影响；没有则省略]
- 关联：[提交、Q／FB、讨论或成果位置]
```

不逐次登记读文件、改草稿、运行格式检查或子代理消息。需要表达原因时融入成果摘要，不另复制整段需求与裁决。

## DISCUSSION-LOG：实质对话

按 D 编号正序；一轮实质沟通一条，无新增信息的“继续”并入原条目。

```markdown
## D-编号：讨论主题

- 日期：[可核实日期]
- 用户提出：[要求、纠正或决定的精炼原意]
- 回应与结果：[实际回应及产生的变化，区分建议与批准]
- 关联：[当前主记录与必要历史来源]
```

这是保存讨论过程的主位置。工具调用、长输出与逐次排错放 agent 记录；不得把未经执行的建议写成已经完成。

## 验收：当前范围与版本证据

先列“范围｜当前结论｜版本／环境｜证据”，后按版本／阶段保存记录。

```markdown
## 版本／阶段：验收对象

- 条件：[要满足的行为与范围]
- 版本与环境：[可确定的版本、环境；未知项如实写]
- 方法与结果：[实际执行及结果，未执行项明确列出]
- 用户验收：[有确认则注明来源和范围，否则写未确认]
- 限制与证据：[未覆盖部分、证据链接]
```

旧结果明确所属版本，不与当前结论并列争夺效力。普通文档检查并入 DEVLOG，不每次新建验收章节。

## 规划、规范与指南

按主题组织，顺序为目的／范围 → 当前规则或操作 → 边界与候选 → 必要来源。章节标题使用主题名称，不使用“日期＋增补”“第几轮处理”。未来方案标清待定或已批准待实施；规范正文不保存讨论、实现或验收的事件序列。

规划默认使用“目标与成功条件 → 当前基线 → 分主题方案 → 后续范围与待定问题 → 依据”；每个方案明确适用阶段与确认状态。规范默认使用“适用范围／版本 → 定义 → 规则与契约 → 异常和兼容边界 → 验证要求”。指南默认使用“适用对象与前提 → 操作步骤 → 结果确认 → 常见异常 → 相关入口”。仅建立有实际内容的章节，不为统一外观新增无用章节。

## README：项目入口

```markdown
# 项目名称

[一句说明用途、使用者和当前可用范围]

## 开始使用
[最短可执行步骤、所需前提和结果确认]

## 当前能力与边界
[实际能力；必要时链接已批准的后续规划，不复制规划规格]

## 开发与验证
[本项目适用的命令或维护方式；非代码项目可省略]

## 文档入口
[按读者任务组织的少量主入口]
```

README 不承载逐轮交付、环境排错历史、提交清单或“本轮未修改”说明。当前使用确需知道的环境限制保留操作结论，诊断过程链接到对应证据。

## Agent 接续记录：最新现场

```markdown
# 任务恢复点

- 身份：[更新时间、执行者、项目、分支／目录、可确定的 BASE／HEAD]
- 目标与授权：[目标、范围与来源链接]
- 已有成果：[文件／提交、对应验证、尚未核实之处]
- 剩余与下一步：[当前阻碍、下一步可执行操作]
- 活动任务：[尚在运行的任务、写入者与文件所有权；没有则写无]
- 证据入口：[必要日志、截图、正式证据位置]
```

checkpoint 替换为最新可接续现场，不追加成会话长卷。逐次命令输出保存到独立 logs 或既有工具记录；正式决定和长期验收证据仍回到相应主记录。完整存储和接手规则见 [记录分层](record-layers.md)。

## 派生视图

默认顺序为当前阶段 → 需用户行动的事项 → 已交付成果 → 阶段候选／未来议题 → 来源。视图只摘要并链接，不另存完整决定或把日志逐条变成请求；零请求时明确表示暂无需介入。具体页面与关系数据按 [视图生成与维护](project-view-generation.md)执行。

整理完成后直接阅读当前表和正文，应能回答“现在是什么、还缺什么、依据在哪里”；若必须顺着多条日期推演才能回答，应继续合并字段并移出过程。
