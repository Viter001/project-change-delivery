# 交付与交接

适用于跨多轮、多人接续、资料冲突或需持续追踪的工作。优先更新现有载体；缺失时建立对应管理占位文件，文件名可沿用项目风格。

## 缺失文件的建立规则

确认当前项目目录与现有载体后，逐项检查以下管理职责。已有等价文件或可访问的管理系统记录则复用，并在项目入口保留定位链接；没有对应载体时建立下列占位文件。不得覆盖同名文件，也不在父级集合目录创建。

| 管理职责 | 默认文件 | 最小占位结构 |
| --- | --- | --- |
| 项目目标与当前状态 | `README.md` | 目标、范围、当前状态、管理文件入口；未知项待补充 |
| Question／Decision：重要变更与裁决 | `QUESTIONS.md` | Q-编号、来源、问题、裁决、落实阶段、关联反馈 |
| Feedback：会议反馈与整改 | `FEEDBACK.md` | FB-编号（保留旧 REVIEW 别名）、来源、反馈、整改、复验、关联 Question |
| 开发记录 | `DEVLOG.md` | 日期、用户要求与决定、工作流摘要、改动、验证结论、剩余事项（不放实时日志） |
| Checks 与验收标准 | `docs/acceptance.md` | 验收条件、验证方法、结果、环境／版本、证据；未执行项标未验证 |

代码／PR Review 优先记录在对应 PR；纯本地可在相关条目或开发记录的代码评审栏记录，不强制另建 REVIEWS.md。会议审查统一称 Feedback，不能把会议意见当作 PR Review 通过。

已有 QUESTIONS.md 继续沿用；已有 REVIEWS.md／VISUAL-REVIEW.md 须先判断内容。会议反馈迁移到 FEEDBACK.md 时保留原记录与 REVIEW-编号或别名映射，更新相关引用；代码评审记录不能盲目改成会议反馈。已有混合 ISSUES.md 则逐项分类并保留映射，不按文件名批量猜类别。不要覆盖同名目标或用户原始资料。开发日志旧名仍可沿用。

专项需求若已有独立管理职责却没有对应文件，例如视觉审查或数据迁移清单，另建对应占位文件并登记入口；不预建与项目无关的专项文件。占位文件至少有标题、用途和待填字段，不能仅创建空文件。已有内容已知时直接填入，不能把当前工作也全部留空。

占位文件不代表需求已裁决、验证已通过或开发已完成。后续工作须更新对应状态。

## 用户记录与 agent 记录

遵循 [记录分层](record-layers.md)：本表中的管理文件面向用户，原始工具输出、实时执行日志、子任务状态和详细恢复点进入 agent 运行目录。用户验收文档保留标准、范围、结果和持久证据入口；不依赖临时日志才能理解交付。

## 四种信息分开维护

| 信息 | 内容 | 更新原则 |
| --- | --- | --- |
| 原始来源 | 用户输入、附件、原始数据 | 保留原件，派生结果引用来源 |
| 决策记录 | 选择、原因、批准来源、适用范围 | 变更时标明取代关系，不悄悄重写历史 |
| 当前状态 | 现在可用的行为、开放问题 | 随有效成果更新，避免照搬历史“全通过” |
| 验证证据 | 对应版本、环境、范围、结果 | 不把计划、历史结果或工具输出中的推断写成本轮实测 |

一个简短条目可以覆盖上述多种信息，不必为四种信息另拆四个文件；这不豁免前节管理职责的载体检查和缺失占位建立。固定编号和版本号沿用项目约定；提交标题与说明使用中文。

## 交付记录的最小内容

按任务需要保留：目标及范围；实际改变；关键决定与原因；验证范围及结果；未完成或未验证项及其影响；成果和证据位置。

例如：

> 已统一三份报告的统计口径，并同步汇总表。按本批数据重算，抽查两组边界值与总额对账通过；旧季度数据未重算，本次不包含历史追溯。下一步由报告负责人确认口径解释。文件尚未对外发送。

这段记录不暗示未来一定要补历史数据；只有用户目标或既有约定要求时才转为待办。

## 接手未完成工作

代理额度耗尽、异常终止或跨工具接续时，按 [协作与中断接手](collaboration-and-handoff.md) 核对任务基线、工作区和仍运行的写入者；以下为通用交接要点。

1. 核对当前成果与最近决策，识别未提交、未发布、部分完成及无关修改；保留原有工作。
2. 将待办与实际成果对照。已有成果若有效则接续，旧计划不作为重新执行依据。
3. 检查证据适用版本。仅重验受后续修改影响或仍存在疑问的部分，不把接手等同于全部重做。
4. 对阻碍下一步的缺口采取行动：补验证、修复当前目标内的问题或询问关键决策。
5. 明确可从哪里继续、剩余什么。责任人未知时写待分配，不能替他人作承诺。

## 完成声明的边界

- “实现已完成”需能指向实际成果；不表示验收或发布完成。
- “验证通过”需说明范围；若必要检查仍失败，不能用部分通过掩盖。
- “用户已验收”需有相应确认；沉默、时间经过或代理推测不算确认。
- “已发布／已发送”需对应真实外部动作与结果；本地文件、提交或预览均不足以证明。
- 仅整理文档时，可声明整理完成，但不能据此声明底层功能已修复。

对外说明与内部记录冲突时，先核对来源。可以纠正已明确的过度声明；若只有历史记录，应写“最近记录显示……”并说明未重新验证，不制造当前实测结论。
