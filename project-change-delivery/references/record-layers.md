# 按受众分层记录

## 用户层：项目发生了什么

README、QUESTIONS、FEEDBACK、DEVLOG 和验收文档面向项目使用者或负责人。写目标、决定及原因、改动结果、验证范围、剩余问题。DEVLOG 包含用户沟通中的有效要求与决定，以及 agent 实际工作流的简明摘要，保留原四条规则的追溯目的。

不放长篇命令输出、工具调用流水、轮询结果、子代理消息全文、每次尝试的堆栈。重要错误应解释影响与下一步，而不只粘贴原始报错。正式验收证据需持久保存，使用户无需翻 agent 临时目录也能判断交付结论。

## Agent 层：下一位执行者如何继续

默认结构如下，按需建立；这是运行状态目录，不是新的调度系统，也不是 `.agents/skills` 技能安装目录：

```text
.agent/
  runs/
    <task-id>/
      <run-id>/
        checkpoint.md    当前恢复摘要，优先读取
        events.jsonl     可选：关键执行事件，不是完整聊天
        logs/            可选：必要的工具、测试与错误输出
        evidence/        可选：运行期截图、报告与其他证据
```

以稳定 Issue ID 或任务 ID 关联，run-id 唯一区分每次运行。checkpoint 至少记录更新时间、执行者、项目/分支/工作目录、可确定的 BASE/HEAD、已有修改、验证对应版本、剩余工作、下一步、仍运行的子任务及证据位置。无 Git 时明记无基线，不能填假 SHA。

只由本次运行的负责人更新 checkpoint，原子替换或采取等价防止半写措施。并行代理分别写各自 run 目录，协调者汇总；不得并发追加同一个日志而假设不会损坏。接手者新建自己的 run，并引用前次 run；先确认旧执行者停止重叠写入，不覆写前任证据。run 目录与任务认领不是文件锁，仍遵循协作工具的状态确认。

恢复摘要在关键提交、验证完成、方案改变或阻塞时更新。即使额度突然耗尽，也有最近恢复点；若最后一次写入不完整或过时，用实际文件、Git 和工具状态核对，不盲信日志。

已有 dsh-crew 等工具提供日志时优先记录访问方式与位置，不复制全部输出。若日志只能被原宿主读取，需把接手必需的摘要和必要片段保存到项目内的运行目录，确保接手者可读。不记录模型隐私推理、令牌或无关敏感资料。

## 读取与提升

接手顺序：用户目标和决定 → 当前任务 checkpoint → 相关差异和必要日志 → 继续剩余工作。不是先遍历所有历史实时日志。

一次排错可以有几十条内部事件，但用户 DEVLOG 只需一条：问题原因、处理结果、实际验证及限制。已确认且影响用户的决策及时提升到用户记录；不得只藏在 agent 日志中。需要长期保留的验收报告整理到项目正式证据位置，例如 `docs/evidence/<task-id>/`，再由验收记录引用。实际路径沿用项目约定，不复制原始日志充数。

示例：
- agent checkpoint：导出修复已提交，存在未跟踪测试夹具，预览检查通过，实际导出未检；接手需先核对夹具，用户另改封面不要暂存。
- 用户 DEVLOG：导出日期修复进行中，预览已通过，实际导出验证待完成。

## 存储、同步与清理

`.agent/runs/` 默认作为本地运行资料，建议在建立时将该精确路径加入项目 `.gitignore`（保留已有规则，不使用笼统忽略 `.agent/`）。不会因为它被忽略就自动删除；同机换 agent 可读取，跨机接手则在授权后交接必要摘要或将整理后的记录纳入版本管理。隐藏目录和 gitignore 都不是访问控制。

用户记录与持久证据按项目规则提交；实时日志默认不提交、不上传 GitHub。Issue 同步只处理规则已选定的业务字段，不上传运行目录、工具输出或 checkpoint。`.issue-sync/` 仍是独立的机器同步状态，不混入用户日志；本次分层不自动迁移或改动其现有格式。

没有明确保留策略或清理授权时，不自动删除运行历史；尤其不得删活动运行、唯一恢复点和未归档证据。此规则不授权清理历史工作区。只读咨询和极小且无接续需要的任务不强制生成运行目录。
