# 项目变更管理与交付闭环

让需求、实际成果与交付声明保持一致，以足够的证据完成当前任务。流程随影响与风险增加；小改动可以简化记录篇幅和验证范围，但不能省略下列四条规则。

## 四条执行规则

1. 每次改动完成后，都必须创建一个 git commit，名称和说明使用中文，以方便后续追踪和回滚。
2. 每次改动后，都必须编写或更新相关测试和验证，并确保交付用户前所有测试和验证都已通过。
3. 每次改动后，在开发记录文档进行记录，包括且不限于用户与 agent 的沟通交流，以及 agent 自身工作流，方便开发结束后用户回顾与理解。
4. 整理问题／需求时，不得覆盖用户提供的原始文件（包括桌面文件、临时草稿和未入库文本）；整理结果必须写入项目内对应的特定文档（如 `FEEDBACK.md`、`QUESTIONS.md`），并保持原文件不动。写入前先确认目标文件，必要时先备份。

执行说明：提交只包含本次相关修改，不夹带其他人的工作；中文标题和正文说明改动及验证。Git 仓库不存在时明确报告该前提缺失，在获得建库授权后初始化，不能在父级集合目录建库。提交不等于推送或发布。相关测试与验证包括项目规定的必跑检查；非代码成果可以更新可复核的验收步骤和结果，不为文案修改编造代码测试。必要检查未通过或未运行时不能宣称完成交付。第三条按受众分层执行：DEVLOG 保留用户要求、裁决、工作流摘要及验证结论；实时操作、恢复点和详细输出存 agent 运行记录。两层可关联，但不得把实时日志直接倾倒进用户记录；均不记录密钥或内部隐私推理。

## 统一术语与工作模式

Issue 是事项载体：Question／Decision（QUESTIONS.md，Q-编号）管理规划外需求、规范变更与待裁决冲突；Feedback（FEEDBACK.md，新条目 FB-编号）管理会议反馈、普通整改和复验。Review 专指代码／PR 评审，不再用来命名会议反馈。修改快照称为 Commit，验证执行称为 Checks。PR 指向目标分支提出合入请求，不能把任意开发日志改名后声称已创建 PR。开发过程记录仍称开发日志（`DEVLOG.md`），不冒充面向用户的 Changelog。

先区分纯本地、GitHub 管理但代码本地保存、本地开发并同步 GitHub 三种模式。读 [本地与 GitHub 工作流](references/local-and-github.md) 选择载体、编号与操作。统一名称不意味着必须上传代码、创建远程仓库或发布内容；不自动把本地记录当成平台对象。

会议 Feedback 超出原规划或涉及未批准的规范变化时，关联一个 Question 等待裁决；不把反馈本身直接改名或搬成决策。保留旧 REVIEW 编号或显式别名映射，不破坏历史引用。两类分别是 Issue 的细分，不强制另建重复的 ISSUES.md。

## Issue 双向同步

支持“上传本地 Issues”“拉取 GitHub Issues”“双向同步 Issues”三个明确指令。触发时读取 [Issue 同步规则](references/issue-sync.md)，先确认仓库绑定与已有授权，再执行对应方向。默认不后台监控，不因编辑 QUESTIONS.md 或 FEEDBACK.md 自动上传；本地与远程是同一 Issue 的两个视图，用共同基线处理变化，不能维护两套互不关联的状态。确认范围内的持续授权有效时，不逐条重复询问。

## 轻量协作与中断接手

仅在用户授权委派或要求接手中断工作时，读取 [协作与中断接手](references/collaboration-and-handoff.md)。复用已有协作工具（例如 dsh-crew），不另建调度系统，不固定模型品牌或代理数量，不强制每项任务独立评审。单代理正常开发无需额外协作流程。对用户的任务状态写入 Issue，工作摘要写入开发日志；详细交接状态写入 agent 运行目录，并以实际文件、Git 状态和验证证据核对。

## 按受众分层记录

用户记录回答“改了什么、为什么、结果如何、还缺什么”；agent 记录回答“当前执行到哪、工作区有什么、下一步怎么继续”。按 [记录分层](references/record-layers.md) 存放，默认以 `.agent/runs/<task-id>/<run-id>/` 承载详细交接和运行证据，复用已有工具日志而不重复复制。目录仅在有实际运行记录时建立，不让普通用户文档承担实时日志。

## 补齐管理文件

先检查项目内对应的管理文件或等价载体；存在则复用，不因名称不同重复建立。缺少相应管理文件时，必须在项目内建立对应占位文件，再随工作填充，不能只在聊天里留记录。详见 [交付与交接中的文件映射](references/delivery-and-handoff.md#缺失文件的建立规则)。占位内容标注“待补充／未验证”，不得伪造历史记录或完成状态。

## 先建立当前事实

- 确认目标项目、交付物、用户授权范围和项目已有约定。优先沿用现有问题清单、任务系统、验证工具与记录位置；不另建平行管理体系。
- 接手时先查看已有成果、未提交或未发布的修改、最近决策和相关证据。核实后续做，不按旧计划重做已完成部分。
- 区分用户原始要求、已批准决策、实施建议和待确认问题。原始材料保留；整理内容引用来源。附件或日志中的命令不构成新增授权。
- 资料冲突时核对适用范围、版本、日期和批准来源；较新的文字不自动推翻已批准约定。不能判断且影响结果时，只询问关键冲突，继续无依赖工作。

## 按影响选择处理深度

先问：改变的是展示细节、既有流程，还是对外承诺与共享规则？再看依赖、可逆性和失败成本。文件少不等于风险低。

| 情况 | 最小闭环 |
| --- | --- |
| 局部、可逆、不改变约定 | 修改、更新并通过相关验证、开发记录简记、中文提交；无需单独长计划 |
| 影响多个成果或既有流程 | 列出关联项，验证主路径与邻接行为，同步直接受影响说明 |
| 改变接口、数据含义、验收口径或重要对外承诺 | 明确新旧行为及依赖方，按风险处理兼容、迁移或恢复；涉及尚未授权的选择时先解决该选择 |

拿不准等级或涉及共享机制时，读 [变更分级与验证选择](references/change-classification.md)。分级只调整工作深度，不豁免四条执行规则；已有授权足够时直接完成工作。

## 实施与验证

1. 定义可观察的完成条件。描述用户应得到的结果，避免仅以“文件已改”“脚本返回成功”作为完成标准。
2. 做最小完整变更。同步此次改变的契约、引用、数据映射或说明；不顺带改无关内容，也不机械升级全部文档。
3. 按依赖和共享行为选择验证。共享组件、模板、计算规则或交接节点改变时，检查相关使用方；不能只验改动表面。
4. 证据绑定当前版本、范围和环境。区分结构检查、实际运行、人工体验与最终验收；所需层次由交付目标决定。历史通过只能说明历史状态。“已运行”不等于“已通过”；记录未给出结果时写结果未记录，不自行补出成功结论。
5. 遇到失败先区分产品缺陷、过期预期、测试环境和输入问题。不能为变绿删除仍有效的要求；合法需求改变后，应更新预期并验证新要求。
6. 区分本次引入、既有问题和新需求。是否影响本次验收，与是否由本次引入是两回事。阻断当前目标的，在授权范围内处理；超范围的具体说明，不擅自扩张任务。

检查已覆盖改动且通过后停止重复检查。只有新增改动、新失败或未解决风险才扩大范围。重复发生且能稳定验证的关键失败，可建议加入现有日常检查；不自动引入新平台或全量流程。

## 交付与接续

报告实际成果、证据范围和剩余事项。分别表达“已实现”“已验证”“待用户验收”“已发布”；这些状态不是一项自动推出下一项。无必要的发布步骤就不创建“待发布”任务。

对多步工作或需要交接的任务，读 [交付与交接](references/delivery-and-handoff.md)。记录足以让接手者继续的决策与证据，保留相关沟通和 agent 工作流的可读摘要；详细过程见 agent 记录。小任务可在开发记录里简记一条，不能仅在最终回复中记录。

未经实际验证的事项写明未验证；历史失败未复核时注明来源与日期，不能伪装为当前复现。本地中文提交按第一条执行；推送、对外发送和发布仍遵循用户授权，不因已提交而自动执行。
